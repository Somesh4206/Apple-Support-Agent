# Decision Log — Apple Support AI

Engineering decisions with rationale. Status tags show when a decision was
made/implemented. Metrics quoted here come from executed runs (see
`data/processed/pipeline_run.json`, `data/processed/eda_summary.json`).

---

## D1. Scope the project to AppleSupport conversations *(Phase 1)*

**Decision:** Filter the Customer Support on Twitter corpus to conversations in
which the `AppleSupport` account participated.

**Why:** AppleSupport is the #2 outbound account by volume (106,860 support
tweets in twcs, behind AmazonHelp's 169,840) and, unlike the top account, its
threads are single-brand support conversations with a clear agent/customer
structure — ideal for intent classification and evidence retrieval. 80,966
AppleSupport conversations (106,137 customer↔support pairs) is plenty for a
grounded-support-agent assignment while staying cheap to process.

**Alternatives rejected:** AmazonHelp (higher volume, but mixed commerce
fulfilment topics that blur "support intent"); multi-brand (would require a
brand-conditioned architecture — unnecessary complexity for the assignment).

---

## D2. AppleSupport identification via configuration + discovery utility, never hard-coded *(Phase 1)*

**Decision:** The support account is read from `APPLE_SUPPORT_AUTHOR_ID`
(environment/.env). `scripts/find_author_ids.py` lists the most frequent
outbound author ids so the value is *discovered from the data*, and the
pipeline fails with actionable instructions when it is unset.

**Why:** twcs.csv has no brand column; outbound `author_id`s are account screen
names while inbound ones are numeric. Hard-coding a guess would be unverifiable
and would silently break on other exports of the corpus. The discovery run
confirms `AppleSupport` (106,860 tweets) without us inventing an id.

---

## D3. Reconstruct conversations from reply links (a reply forest) *(Phase 1)*

**Decision:** Build parent→child trees from `in_response_to_tweet_id` (each
tweet has ≤1 parent) and reconstruct threads depth-first from their roots;
`response_tweet_id` is used only for closure expansion and consistency
diagnostics.

**Why:** Customer↔support pairs and RAG evidence both require the *thread*
context, not isolated tweets. Single-parent links give a clean tree; the
comma-separated `response_tweet_id` field is redundant/noisier (14,005 dangling
child links observed vs 0 parent-link mismatches in our run), so we treat the
parent link as authoritative.

**Ordering detail:** tweet ids in twcs are *not* time-ordered (verified:
replies can have larger ids than the tweets they answer and timestamps are
sometimes inconsistent), so conversation order is structural (DFS from root,
siblings by timestamp, file-order tiebreak) — never id-based.

---

## D4. Conversation identity preserved end-to-end (`conversation_id`) *(Phase 1)*

**Decision:** Every tweet and pair carries the root tweet id of its thread as
`conversation_id`.

**Why:** Phase 2 must split train/val/test at the *conversation* level to
prevent leakage (spec §9). Isolating the golden set and doing
conversation-level splits both depend on this id existing from day one.

---

## D5. All identifiers parsed as strings *(Phase 1)*

**Decision:** `tweet_id`, `author_id` and both link columns are read with
`dtype=str, keep_default_na=False`.

**Why:** Twitter ids are 18–19 digit numbers; float parsing silently loses
precision and would corrupt the reply graph. Empty-string handling (instead of
NaN) also prevents "NA"-like author handles being dropped as missing.

---

## D6. Conservative text cleaning *(Phase 1)*

**Decision:** Remove only obvious Twitter artifacts: HTML entities (10,426
decoded), RT prefixes (2), URLs (99,269), the leading addressing @mention
(187,230), collapsed whitespace (19,765). Preserve typos, casing, punctuation,
product terms. Drop rows that are empty after cleaning (787) or have missing
identifiers (0).

**Why:** The corpus must stay realistic for embedding-based classification and
retrieval (Phases 3–4). Over-normalisation (lowercasing, stopword removal,
lemmatisation) would erase exactly the signals — typos, product names, urgency
punctuation — that make intent detection and similarity matching realistic.

---

## D7. Raw data never committed; outputs reproducible *(Phase 1)*

**Decision:** `data/raw/*.csv` (516 MB twcs.csv) is gitignored; processed
outputs are regenerated by `scripts/prepare_data.py` and recorded in
`pipeline_run.json` (mode, settings, per-stage stats, validation results).
A clearly-named `twcs_synthetic_sample.csv` generator exists for smoke tests
without Kaggle access; any run on it is flagged `synthetic: true` in outputs.

**Why:** The assignment explicitly forbids committing twcs.csv; reproducible
run metadata is the honest alternative to committing derived data.

---

## D8. AppleSupport-first chunked closure instead of full in-memory load *(Phase 1)*

**Decision:** At full scale the pipeline scans the file in 200k-row chunks and
collects AppleSupport threads via multi-pass closure (record author tweets →
expand to parents/children → repeat), rather than loading all 2.8 M rows into
RAM.

**Why:** The execution environment has ~4 GB RAM; a full string-typed load
(~2–3 GB) risks OOM. The collector keeps peak memory at a few hundred MB and
finishes in ~212 s (12 passes). Documented limitation: closure truncates
extremely deep threads if the pass budget is exhausted (residual +41 tweets at
pass 12, ≈0.017% of collected tweets) — pairs are unaffected because **all**
support replies are recorded in pass 1.

---

## D9. Pipeline validation as the Phase 1 test gate *(Phase 1)*

**Decision:** `prepare_data.py` runs 7 structural validations after building
outputs (pair endpoints exist; pairs map to conversations; non-empty pair
messages; unique response ids; responses authored by the configured account;
unique conversation ids; tweets attached to conversations) and exits non-zero
on any failure.

**Why:** "Working and tested" for a data phase means provable invariants on
the artifacts, not just absence of exceptions. The executed run reports 7/7
PASS; the same gate re-runs on every regeneration.

---

## D10. EDA script + notebook share one source of truth *(Phase 1)*

**Decision:** `scripts/run_eda.py` computes all statistics and writes
`eda_summary.json` (+ PNG charts); the notebook `01_data_exploration.ipynb`
performs the same analysis interactively and cross-checks 16/16 values against
the summary file; the web dashboard reads the same JSON.

**Why:** Three consumers (notebook, dashboard, report) must never disagree.
The cross-check in the executed notebook (16/16 assertions passed) is the
consistency test.

## D11. Provisional keyword topics are EDA input, not a classifier *(Phase 1)*

**Decision:** Topic tagging in Phase 1 is transparent word-boundary keyword
matching over customer messages, explicitly labelled *provisional*; the final
taxonomy is a Phase 2 deliverable informed by these frequencies.

**Why:** The assignment forbids claiming a data-derived taxonomy without
supporting analysis. The keyword matcher initially used substring matching and
inflated "Software/Apps" to 64.5% (`app` matching inside `apple`); switching to
word boundaries produced the honest distribution (Software/Apps 29.0%,
Device/Hardware 14.1%, …, multi-topic 9.9%) — recorded here as a reminder of
why tagging mechanics must be documented.

---

## D12. Historical replies are evidence, never policy *(Phase 1)*

**Decision:** The corpus is described throughout (README, report, notebook,
dashboard, generated outputs) as *historical* evidence for retrieval and
evaluation — not a representation of current Apple policy.

**Why:** The corpus spans 2013–2017 (observed timestamps). Product lines,
prices, warranty terms and support procedures have changed; presenting old
replies as current policy would be unsafe. This framing is a standing
requirement for Phases 5–6 (generation must phrase retrieved content as
"based on similar historical support cases…").

---

## D13. Taxonomy derived from EDA + manual reading of the unmatched pool *(Phase 2)*

**Decision:** The final 10-class taxonomy (`src/intents/taxonomy.py`) keeps
every EDA provisional topic above ~2% share as its own class, merges
sub-2.5% topics that share a routing profile (Account+iCloud;
Billing+Refunds+Orders+Subscriptions), and splits the 53% keyword-unmatched
pool into three observed behaviours (venting / support-process meta-complaints
/ other). Each class carries an EDA anchor, escalation hint and examples;
`typically_escalated` is recorded per class for Phase 6.

**Why:** The assignment forbids inventing a taxonomy without supporting
analysis. The EDA distribution (measured over 106,137 messages) is the
quantitative justification; the unmatched-pool split is justified by reading
50 random openers — pure venting and "let me talk to a human" complaints are
routing-relevant behaviours a keyword topic list cannot express. Merging keeps
rare classes from having unusable golden support (~1 example).

**Alternatives rejected:** keeping all 11 EDA topics separate (billing 2.4%
alone ≈ 5 golden examples — too few); an `unmatched` dump class (mixes
escalation-worthy and not); splitting Software/Apps (29%) into OS vs app
faults (the app slice would land ~5% ≈ 10 examples).

---

## D14. Golden set: uniform sample, manual labelling, blind worksheet, hard validation gate *(Phase 2)*

**Decision:** 200 conversation openers sampled uniformly (seed 42) from the
80,244 customer-initiated roots — no rare-class boosting. Labels written by
hand after reading every message, from a worksheet that shows NO keyword
hints. `build_golden_set.py build` refuses to produce artifacts unless every
row is labelled exactly once with a valid taxonomy label.

**Why:** The golden set must estimate performance on the *natural*
distribution (accuracy on this corpus is the deployment-relevant number);
boosting would bias it. Blind labelling avoids circularity — labelling from
the same keywords that drive the keyword baseline would inflate that
baseline. The gate makes "working and tested" checkable: invalid or missing
labels exit non-zero. Limitations honestly recorded: single labeler, rare
classes with 1–2 test examples (report §15).

**Alternatives rejected:** weak/distant supervision from the Phase 1 keywords
(circular — the keyword baseline would score ~1.0); LLM-assisted labelling
(the assignment expects human judgement for the golden set; also unverifiable
here); 500+ examples (labelling cost vs marginal metric stability).

---

## D15. Conversation-level stratified split + golden isolation manifest *(Phase 2)*

**Decision:** Splits key on `conversation_id` (70/15/15, stratified by label,
per-class rounding to train, seed 42). `golden_conversation_ids.json` lists
all 200 conversation ids for Phase 4 retrieval to exclude from its evidence
index.

**Why:** Spec §9 demands conversation-level splitting (tweet-level splits
leak near-duplicate texts across train/test). Stratification keeps every
class present in val/test where its support allows it. The manifest enforces
golden-set isolation — evaluation material must never become retrieval
evidence — which is only possible because D4 preserved conversation identity
end-to-end.

---

## D16. Baselines: measure honestly, tune on train-CV, report the failure *(Phase 2)*

**Decision:** Three baselines on the golden set — keyword rules (Phase 1
topics mapped to labels, word-boundary matching per D11), majority class,
and TF-IDF+LogReg with a 16-config hyperparameter grid selected by 5-fold CV
ON THE TRAIN SPLIT (criterion: mean(accuracy, macro-F1)). Val stays a
held-out sanity check; test is untouched until the final evaluation. The
headline result is reported as measured: majority wins accuracy (0.655),
keyword rules win macro-F1 (0.391), the learned baseline collapses to
`software_bug` (0.621 / 0.078).

**Why:** Tuning on the 29-example val split was tried first and produced a
config (C=0.01, balanced) that scored 0.412 val macro-F1 but 0.104 on test —
selection noise, recorded in `baseline_results.json`. Train-CV uses ~5× more
data for selection. The composite criterion exists because accuracy-only
picks a majority-collapser while macro-only picks an accuracy-collapser —
the assignment needs both numbers to be meaningful. Reporting the collapse
is the point: it is the measured motivation for Phase 3 embeddings, and the
confusion matrix (25/29 predicted `software_bug`) makes the failure mode
inspectable rather than asserted.

---

## D17. Frozen encoder + learned head, evaluated under the Phase 2 protocol *(Phase 3)*

**Decision:** The Phase 3 classifier is `all-MiniLM-L6-v2` (from
configuration, `EMBEDDING_MODEL` — never hard-coded) kept **frozen**, with
two heads fit on the 142-example train split only: a multinomial
LogisticRegression head (hyperparameters C × class_weight selected by
5-fold CV on train, criterion mean(accuracy, macro-F1) — *identical* to
D16) and a zero-hyperparameter nearest-centroid head with cosine
confidence. Val remains a sanity check; test untouched until final
evaluation; embeddings cached on disk keyed by (model id, texts hash) for
determinism.

**Why:** With n_train=142, fine-tuning a 22.3M-parameter encoder would
memorise the split and leak evaluation signal through the representation;
the frozen-encoder + linear-head recipe is the honest transfer-learning
baseline at this scale. Reusing the D16 protocol exactly is what makes the
Phase 2→3 comparison meaningful: the only changed variable is the feature
representation (lexical TF-IDF → semantic embeddings). The prototype head
is included because it needs no tuning at all, naturally tolerates
2-example classes, and exposes a confidence surface — the measured result
(macro-F1 0.389, best of all learned models) validates that simplicity.

## D18. Report the class-collapse fix, not a fake accuracy win *(Phase 3)*

**Decision:** The Phase 3 headline is stated as measured: embeddings lift
test macro-F1 0.078 → 0.303 (LogReg head, ≈3.9×) at accuracy 0.6552 —
*tying* majority, not beating it — and weighted-F1 0.6586 (best of all
five models). The centroid head wins learned macro-F1 (0.3894) at lower
accuracy (0.5517). Rare-class over-sampling is reported as a measured
comparison (balanced class weights: CV macro-F1 0.3495 → 0.4288, selected
by the criterion), and the confidence preview at threshold 0.60 carries an
explicit n=29 indicative-only caveat.

**Why:** At n=29 test examples, +0.03 accuracy is one tweet; presenting it
as a breakthrough would be dishonest. The real, inspectable change is
structural: the head predicts 7 distinct classes vs 2 for TF-IDF (25/29
`software_bug`), and per-class F1s move from 0.0 to non-zero across rare
classes. Documenting the sarcasm error made *with 0.889 confidence* also
pre-weights Phase 6 against confidence-only escalation — recorded now so
the later policy design cannot quietly ignore it.

## D19. Recall@K relevance = Phase 3 head label agreement *(Phase 4)*

**Decision:** The retrieval corpus is unlabeled, so a relevance function
had to be *chosen* and documented rather than assumed. Every corpus pair
is labelled by the Phase 3 `logreg_head` (test accuracy 0.6552, macro-F1
0.3032) over the same embeddings the index uses; a hit at rank ≤ k is a
retrieved pair whose predicted label equals the opener's golden label.
The proxy's noise is reported as part of the measurement (the head's own
metrics are restated wherever the relevance numbers appear), and five
qualitative examples (3 hits + 2 no-hits) let a reader judge semantic
similarity directly, unmediated by the classifier.

**Why:** The alternatives were worse or circular: same-conversation
retrieval is impossible by design (golden conversations are excluded —
that is the point of the isolation manifest), human-labeling 105,871
pairs is out of scope, and keyword overlap was already measured in Phase
2 as a weak intent signal. The Phase 3 head is the best measured
classifier available, uses the same encoder (so relevance shares the
retrieval geometry), and — decisively — its errors are *inspectable*
through the Phase 3 error analysis. A future calibration pass
(human-label a small retrieval sample) is recorded as the standing
improvement lever in report §16.

## D20. Exact flat index, not approximate *(Phase 4)*

**Decision:** `faiss.IndexFlatIP` over L2-normalised 384-d vectors —
exact cosine similarity, 105,871 × 384 float32 (~155 MB), brute-force
search — with a saved id-mapping sidecar and a structural
self-retrieval check (a corpus vector must return itself at rank 1 with
score ≥ 0.999; measured 1.0000). The corpus embedding is chunked into
5k-text cache files so an interrupted 20-minute CPU encode resumes
instead of restarting.

**Why:** At ~106k vectors, exact search is sub-millisecond per query on
CPU — IVF/HNSW would add nprobe/cluster knobs and recall loss for zero
measurable latency win, and exactness keeps Recall@K reproducible (no
clustering seed to document). The chunk cache exists because the first
attempt (single 106k-text embed, batch 256) spiked memory enough to
trigger a kernel OOM against the resident dev server on a 4 GB box;
batch 64 in 5k chunks caps the spike under ~1 GB while keeping the
determinism guarantees (cache key = model id + texts hash; batch size
never changes the values).

## D21. Live retrieval behind a lazy-loading mini-service *(Phase 4)*

**Decision:** The dashboard's "try it" demo talks to a real HTTP service
(Bun on port 3030 wrapping a persistent Python worker over stdio
JSON-lines) that lazily loads the encoder + FAISS index + corpus +
intent head on the first request (~15 s, one-time) and then answers
searches in ~80 ms. The worker also reports the query's predicted intent
(Phase 3 head) alongside each retrieved pair's precomputed predicted
intent. The frontend reaches it only through the sandbox gateway as a
relative URL with `?XTransformPort=3030` — never an absolute
localhost URL.

**Why:** A live index search is the first genuinely interactive ML
feature the dashboard has had, and it demonstrates the actual artifact
(the same 105,871-pair index the Recall@K numbers were measured on)
rather than a canned screenshot of it. Lazy loading keeps the ~830 MB
resident cost off the box until someone actually uses the demo — the
memory budget is shared with the Next.js dev server, which this round's
kernel OOM history makes a first-class constraint. The unsolicited
`event: loading/ready` protocol lets the UI show an honest "warming up"
state instead of a frozen spinner.

---

## D22. Generation as an extension of the retrieval service *(Phase 5)*

**Decision:** Grounded generation lives in the *same* mini-service as
retrieval (Bun :3030) as `POST /api/phase5/generate`, not in a Next.js API
route. One request does the whole Phase 5 pipeline: embed → FAISS top-K →
Phase 3 head intent/confidence → grounded prompt → z-ai-web-dev-sdk LLM
(backend-only; the SDK is never imported client-side) → per-reply heuristic
scoring. Thresholds (TOP_K, INTENT_CONFIDENCE_THRESHOLD,
RETRIEVAL_THRESHOLD) are parsed from the project `.env` so the service and
`src/config.py` share one source of truth. The offline evaluation
(`scripts/evaluate_generation.py`) is a thin HTTP client over this endpoint,
which makes the live dashboard demo and the recorded metrics run the exact
same code path.

**Why:** The service already owns the ~830 MB resident artifacts and the
lazy-load lifecycle; a separate generation service or a Next.js route would
either duplicate that memory or push it into the memory-fragile dev-server
process. One code path for demo + evaluation removes drift between what the
dashboard shows and what the report claims. The SDK import under Bun was
verified before wiring (glm-4-plus confirmed from the completion object,
not hard-coded).

## D23. Six safety rules in the prompt; one prompt iteration *(Phase 5)*

**Decision:** The system prompt encodes assignment §16 as six
non-negotiable rules: (1) evidence-only facts — no invented prices, dates,
versions, policies, links; (2) an explicit historical grounding phrase
("Based on similar cases we've seen, …") that never implies current policy;
(3) on weak evidence, ask ONE clarifying question instead of guessing;
(4) for account/payment/security, redirect to DMs and never solicit personal
details in public; (5) evidence-matched warm/concise style, no hashtags or
emoji; (6) ≤280 characters. The user prompt carries the Phase 3 intent +
confidence (with runner-up) and an explicit evidence-quality line (top-1
cosine vs RETRIEVAL_THRESHOLD, phrased "strong/weak grounding"), so the
generation genuinely consumes the Phase 3/4 signals. Rule 2 was strengthened
after the first (unrecorded) evaluation run showed ~45% framing compliance
("make it clear…" → "include a brief grounding phrase…"); the recorded run
then measured 100% compliance. The prompt iteration is disclosed rather
than hidden — the recorded artifacts describe the final prompt only.

**Why:** §16 compliance that is merely *hoped for* is not measurable; rules
phrased as required output surface (a phrase family the scorer can regex)
make the safety framing both enforced and checkable. Feeding the
intent/confidence and evidence-quality into the prompt (not just recording
them) means the LLM itself degrades gracefully on weak evidence — the
behaviour the Phase 6 policy will gate.

## D24. Honest heuristic reply scoring; no LLM-as-judge *(Phase 5)*

**Decision:** Reply quality is measured only with transparent lexical
heuristics, all implemented once in the service and reused by the
evaluation: grounding overlap (share of stopword-filtered reply tokens
present in the top-K evidence pairs), unsupported specifics (numbers /
version-like tokens / prices / URLs absent from the evidence), safety
framing compliance, clarifying-question / DM-redirect presence,
personal-data *solicitation* (advising a password change is explicitly not
flagged — only asking for / repeating private details is), reply length vs
corpus style, and latency. Escalation consistency previews Phase 6: among
replies whose gates fail, the reply must ask a clarifying question or
redirect to DMs. Every metric ships with its definition string and five
recorded caveats (lexical proxy ≠ entailment; nondeterministic outputs; no
human annotation; specifics check limited to numbers/URLs; policy not yet
implemented). No LLM grades its own output.

**Why:** An LLM-as-judge loop would score the replies with the same model
that wrote them — circular, uncalibrated and opaque. Lexical heuristics are
reproducible, cheap enough to run per live demo request, and their failure
modes are statable in one sentence each. Recording the caveats *in the
artifact* (not just the report) keeps every future consumer honest.

## D25 — Phase 6 escalation policy: rules, the account_icloud refinement, and no tuning on test labels

**Decision:** The escalation policy is five explainable rules evaluated on
runtime signals only (predicted intent, intent confidence, top-1 retrieval
score, message text): E2 private-state domains (billing_purchases,
repair_warranty, security_privacy, support_process — the Phase 2
`typically_escalated` hints — **plus account_icloud**), E3 unmatched intent
(`other`), E4 sensitive content (payment/order language, email, phone,
card-like number), G1 confidence < 0.60, G2 top-1 < 0.65. Any firing rule ⇒
escalate. The numeric gates reuse the thresholds fixed since Phases 3/4.

**Why:** (1) The taxonomy hints were designed in Phase 2 as routing priors —
consuming them as policy rules closes the loop between design and execution.
(2) `account_icloud` deviates from its Phase 2 hint ("recovery steps are
well covered") deliberately: the golden test set contains a sign-in loop
rejecting a *newly changed* password that passes both numeric gates
(confidence 0.825, top-1 0.769) — exactly the takeover-adjiguous case where
public advice can compound a lockout. Public generic advice in
private-state domains has asymmetric downside; a human minute is cheaper.
(3) Safety asymmetry: a false auto publishes an unreviewed public reply; a
false escalation costs one human review. The policy is therefore designed
to over-fire, and the cost is measured (4/19) rather than hidden.

**Rejected:** learned escalation (a classifier on gate features) — n=29
labels make any learned policy unvalidatable and unexplainable;
threshold tuning on the test labels — that is the definition of leakage.

## D26 — Phase 6 ground truth: single-annotator labels with fixed criteria, recorded before evaluation

**Decision:** The 29 golden TEST openers were labelled escalate/auto_ok by
the author against four fixed written criteria (money/account stakes;
safety/off-topic; ambiguity; unusable device/data at stake), recorded in
`evaluation/escalation_labels.json` with per-message rationale, *before*
running the policy on the set: 10 escalate / 19 auto_ok.

**Why:** Escalation quality needs ground truth, and no external annotator
exists for this assignment. The honest version of a single annotator is:
written criteria fixed in advance, labels + rationale committed next to the
code, the limitation stated (no inter-rater agreement), and exact
Clopper-Pearson intervals attached to every rate so n=29 speaks for
itself. Labels were made on message content; the predicted
intent/confidence were visible to the annotator but the criteria are
content-based, and no label was changed after the policy's decisions were
seen.

## D27 — Phase 7 agent: the policy gates the LLM, and the TypeScript mirror is asserted, not trusted

**Decision:** The unified agent evaluates the Phase 6 policy *before* any
LLM call. Auto-handle ⇒ Phase 5 grounded generation, reply ready to send.
Escalate ⇒ no LLM call at all; the human receives a structured handoff
(fired rules with observed values, top-3 evidence, a deterministic
acknowledgment template labelled "never sent automatically"). The service
implements the policy in TypeScript (same rules, same shared-`.env`
thresholds), and `scripts/evaluate_agent.py` **asserts 29/29 decision + rule
agreement** with `src/escalation/policy.py` on identical signals.

**Why:** Dual implementations drift silently; a consistency assertion turns
drift into a loud test failure. Skipping the LLM on escalation is the
policy made architectural: the unsafe path is not "a careful prompt" but
0 ms and 0 tokens — measured as 48.3% of test calls skipped. The suggested
acknowledgment is a fixed template, not an LLM draft, so nothing generated
is ever published on the escalate path.

## D28 — Phase 8 Streamlit app: a thin client, not a second pipeline

**Decision:** `streamlit_app.py` contains no ML and no LLM code — it is a
UI over the same live `/api/phase7/agent` endpoint the dashboard uses,
verified with Streamlit's AppTest (zero exceptions, both decision paths)
plus live browser screenshots.

**Why:** The assignment asks for a Streamlit app; duplicating the
encoder/index/head/generation stack inside it would double resident memory
(~600 MB), fork the scoring logic, and create a second thing to keep
consistent. A thin client extends the Phase 5 one-code-path decision (D22):
the Streamlit app, the web dashboard and the offline evaluations all
observe the same agent. Its limitation is stated too: it needs the
retrieval service running on :3030.
